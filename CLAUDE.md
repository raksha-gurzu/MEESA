# Meesa Try-On — Project Context

A local Streamlit app that uses Google's **Nano Banana 2** (Gemini 3.1 Flash Image) to perform virtual try-on: the user uploads a photo of a person and a photo of an outfit; the app returns a photorealistic image of that person wearing that outfit.

> This file is the canonical project log. Every decision, scope change, and rationale lives here. Update it as work progresses so future sessions have full historical context.

## Behavior

- Two side-by-side file uploaders: **Person photo** and **Outfit photo**.
- "Generate try-on" button is disabled until both photos are uploaded.
- On click: uploads saved to `images/`, model output saved to `generated/`, all timestamped (`YYYYMMDD_HHMMSS_*.png`).
- After a result returns, the screen shows **three panels side-by-side**: Person | Outfit | Try-on result, plus **Regenerate** and **Download** buttons.
- No user-facing text prompt — the prompt is fixed in `prompt.py`.
- Status text during generation: *"Composing your try-on… (usually 5–10s)"*.
- A small consent caption sits under the title: *"Use only photos you have permission to use. Results include an invisible SynthID watermark from Google."*

## Decision log

### 2026-05-13 — Initial planning session

Held a structured grilling session before writing any code. Recorded outcomes below.

#### Grill 1 — Model choice → **Nano Banana 2 (`gemini-3.1-flash-image-preview`)**

The original plan was to use Gemini 2.5 Flash Image (the original "Nano Banana"). User pushed back: too old. Web-researched current Gemini lineup as of May 2026:

| Tier | Model ID | Speed @ 1K | Cost @ 1K | Quality |
|---|---|---|---|---|
| Nano Banana Pro (Gemini 3 Pro Image) | `gemini-3-pro-image` | 10–20s | $0.134 | Best |
| **Nano Banana 2 (Gemini 3.1 Flash Image)** ✓ | `gemini-3.1-flash-image-preview` | 4–6s | $0.067 | ~95% of Pro |
| Original Nano Banana (Gemini 2.5 Flash Image) | `gemini-2.5-flash-image` | 5–10s | $0.039 | Baseline |

**Decision:** Nano Banana 2. Half the cost of Pro, 2–3× faster, only ~5% quality gap, native multi-image fusion. Image Search Grounding feature (NB2-exclusive) is not relevant here because the outfit is user-supplied. Pin the model ID as a constant in `llm.py` so a swap is one-line if quality disappoints.

**Escape hatch:** swap constant to `gemini-3-pro-image` (Pro) for max quality, or `cuuupid/idm-vton` via Replicate if specialized garment fidelity ever becomes critical.

#### Grill 2 — Outfit input contract → **Accept A + B, defer C**

What kind of outfit photos does the app accept?

- **A. Flat-lay / product shot** (garment on white background) — best quality. ✓
- **B. Reference person wearing the outfit** (Pinterest / Instagram screenshot) — common, works well with NB2. ✓
- **C. Multiple separate garments** (top / bottom / shoes uploaded individually) — deferred; v1 uses a single outfit photo.

**Decision:** Single outfit uploader. The prompt explicitly tells the model to extract only the clothing if a reference person is shown (handles scenario B). UI shows a one-line hint: *"Tip: works best with a clear photo of the outfit. Either a product shot or someone wearing it is fine."* C may be added in v2 if demand emerges.

#### Grill 3 — Person photo contract → **Accept P1 + P2, hint discourages P3 / multi-person**

- **P1. Full-body photo** — best.
- **P2. Waist-up photo** — works; the prompt instructs the model to extend the body naturally only when the outfit demands it.
- **P3. Headshot / face only** — bad results; not suitable for try-on. Discouraged via UI hint.
- **Multi-person photos** — discouraged via the same hint, not programmatically blocked.

**Decision:** No programmatic gating (no face detection, no aspect-ratio heuristic). Single UI hint near the uploader: *"Tip: a full-body or waist-up photo works best. For best results, just one person in frame."* The prompt handles framing preservation and graceful body extension.

#### Grill 4 — Output count → **1 image per generation + Regenerate button**

Considered showing 4 variations like Midjourney; rejected because (a) NB2's first-shot quality is strong, (b) 4× cost is wasteful when most try-ons are usable on attempt 1, (c) cost predictability matters during prototyping, (d) a single confident result feels better than a "least-bad" grid.

**Decision:** Single image per click. A "Regenerate" button issues a fresh call with the same inputs. Each regenerate is its own saved file in `generated/`.

#### Grill 5 — Result screen layout → **Layout B (3-panel side-by-side)**

After generation, the screen shows three panels in a row: **Person | Outfit | Try-on result**, with Regenerate and Download buttons below.

**Decision:** For a try-on app, the *comparison* is the product. Seeing all three at once turns "here's an image" into "here's how this outfit looks on me." Native Streamlit columns — no extra deps. (Streamlit will stack the columns on mobile; acceptable for v1.)

#### Grill 6 — Prompt v1 → **Locked**

Full prompt text is in `prompt.py`. Key design choices:

- **Numbered, capitalized image role labels** ("FIRST IMAGE", "SECOND IMAGE") — NB2 sometimes confuses input order without explicit labels.
- **"IGNORE that person entirely"** — handles scenario B leakage (model extracting features of the reference person, not just the clothing).
- **"Preserve framing, crop, camera angle, background"** — stops NB2 from "improving" inputs (zooming, recropping, changing setting).
- **"Extend the body naturally and minimally"** — handles waist-up photos when outfit includes pants.
- **Negative constraints** ("do NOT add accessories…", "do NOT alter identity…") — shut down common NB2 failure modes (hallucinated jewelry, subtle ethnicity shifts).
- **Style anchor at end** ("photorealistic, professional fashion photography") — NB2 responds to these like Midjourney camera prompts.

**Decision:** Locked as v1. If we tune later, version it (`TRY_ON_INSTRUCTION_V2`) so we can A/B.

#### Grill 7 — Final defaults (all locked)

| # | Decision | Locked value |
|---|---|---|
| 7.1 | Output resolution | **1K** (Nano Banana 2 default). On-screen previews are downscaled anyway; 2K doubles cost for no perceived gain. Saved-to-disk file is at full resolution. |
| 7.2 | Output aspect ratio | **Match the person photo**, snapped to nearest NB2-supported ratio (1:1, 4:3, 3:4, 16:9, 9:16, 21:9, 9:21). Keeps the Person and Result panels visually aligned in the comparison view. |
| 7.3 | Input preprocessing | **RGB convert + 1536px cap on longest edge + EXIF auto-rotate.** Applied to BOTH uploads before sending. Prevents alpha-channel errors, bloated payloads, sideways outputs. |
| 7.4 | File naming | `images/YYYYMMDD_HHMMSS_fff_person.png`, `..._outfit.png`, `generated/..._tryon.png`. Always `.png`, millisecond precision, no sidecar JSON metadata. |
| 7.5 | Regenerate behavior | Photos persisted in `st.session_state`; spinner shows over previous result; latest result only shown (history lives on disk); unlimited regenerates; changing inputs replaces the Regenerate button with Generate again. |
| 7.6 | Loading UX | `st.spinner("Composing your try-on… (usually 5–10s)")` inside the result column; uploaders + Generate button disabled during call; 60s network timeout. |
| 7.7 | Error handling | Friendly `st.error()` for: missing API key (top banner + disabled UI), safety-blocked content, no image in response, network/timeout, invalid input. No tracebacks in UI; logged to stderr only. Uploads and previous result preserved on error. |
| 7.8 | Consent disclaimer | `st.caption()` directly under the title: *"Use only photos you have permission to use. Results include an invisible SynthID watermark from Google."* |
| 7.9 | API key handling | `.env` file + `python-dotenv`. Variable: `GEMINI_API_KEY`. `.env.example` committed as template; `.env` gitignored. |
| 7.10 | CLAUDE.md upkeep | Append a dated entry to "Future-change notes" on every meaningful decision change, scope adjustment, or implementation milestone. Done proactively without user request. |

Out of scope for v1: analytics/telemetry, login/accounts, image-gallery UI, mobile-specific styling, README.md.

### 2026-05-13 — Post-first-test fixes (parser hardening + timeout)

**Real-world latency:** Nano Banana 2 (preview) is highly variable. Direct API tests measured 3s (with `NO_IMAGE` finish on synthetic inputs) and 19–58s (with successful `STOP`) across calls. The documented 4–6s headline figure from Google's blog is best-case; realistic range with real photos is 15–60s.

**Parser bug found and fixed in `llm.py`:**
- `candidate.content.parts` can be `None` (not `[]`) when the model returns a `NO_IMAGE` finish reason. The original parser iterated over it → `TypeError`. Now guarded.
- Split `_BLOCKED_FINISH_REASONS` into two buckets: `_SAFETY_FINISH_REASONS` (SAFETY / PROHIBITED_CONTENT / RECITATION / BLOCKLIST / SPII / IMAGE_SAFETY / IMAGE_PROHIBITED) and `_NO_IMAGE_FINISH_REASONS` (NO_IMAGE / IMAGE_OTHER / OTHER / LANGUAGE / MALFORMED_FUNCTION_CALL). Each surfaces a different friendly message.
- Added `print("[llm] finish_reason=...")` so the terminal shows the actual reason per call — useful for prompt-tuning.

**Other changes:**
- `llm.py`: `TIMEOUT_MS` raised from 60s → 120s. The 57.7s real generation we observed was within 60s but uncomfortably close; 120s gives proper headroom for the preview model's tail latency.
- `app.py`: spinner text updated from *"(usually 5–10s)"* → *"(typically 15–60s with the preview model)"* — sets honest expectations.

**Watch-list:** if `gemini-3.1-flash-image-preview` graduates to a stable ID, swap the constant. If latency stays >30s consistently for end users, consider a "use Pro / 2.5 Flash" model toggle.

### 2026-05-13 — First real-image test + prompt iteration (v1 → v2 → v3)

User provided a canonical test pair:
- **Person photo:** 401×600 woman in beige pant suit, full-body outdoor shot with white pillars in background. (P1 / full-body input — ideal.)
- **Outfit photo:** 1100×1100 teal/mint tulle ball gown with pink floral appliqués, worn by a different model with a flower-crown headpiece. (Scenario B / reference person wearing the outfit — common real-world case.)

Iterated three prompt versions and one bug fix. Total cost: ~$0.21 (3 generations).

**v1 prompt result (33.5s, 896×1200):** Identity preserved ✓, outfit transferred faithfully ✓, but framing got cropped from full-body to waist-up ✗. **Two root causes identified:**

1. **Bug in `_SUPPORTED_RATIOS` (`llm.py`):** The list contained `9:21` (NOT a supported API value) and was missing `2:3` and `3:2`. The person photo's ratio (0.668) was being snapped to `3:4` instead of `2:3` — the wider/shorter canvas was cramping the full body. **Fix:** replaced `9:21` with `2:3`, added `3:2`. Mapper now matches the API enum exactly: `1:1, 2:3, 3:2, 3:4, 4:3, 9:16, 16:9, 21:9`. Confirmed via `types.ImageConfig.model_fields['aspect_ratio'].description`. Re-validate this list if the SDK ever upgrades.
2. **Prompt was too loose on framing.** Added a CRITICAL rule explicitly mapping input crop to output crop.

**v2 prompt result (57.7s, 848×1264 — 2:3 mapping confirmed):** Framing fixed (full gown visible) ✓, but new failures appeared:
- Model added a flower headpiece from the outfit-reference model — that headpiece was not part of the outfit, it was the reference model's styling.
- Pose was hijacked from the outfit reference (cape-spread arms) instead of preserved from the subject (hands in pockets).
- Feet still cropped at the bottom.

**Root cause:** the original "IGNORE that person entirely" was interpreted by Nano Banana 2 as "ignore the second person's identity" but NOT "ignore pose, accessories, or styling."

**v3 prompt — rewrote `prompt.py` from scratch with split-image roles:**
- "Take ONLY these things from the FIRST IMAGE" — face, hair, skin, pose, background, framing.
- "Take ONLY these things from the SECOND IMAGE" — clothing only (colors, patterns, cut, drape).
- "Do NOT take from the SECOND IMAGE, even if visible" — second person's face/pose/expression, any headpiece/crown/jewelry, second image's background/lighting.
- Added a **pose-handling block** with a physical-adaptation escape hatch: hands/arms may adapt MINIMALLY only if physically required by the new garment (e.g., gown has no pockets); default to first-image positions; never copy the second person's pose.

**v3 result (18.9s, 848×1264):** Headpiece gone ✓, pose preserved ✓, white sneakers from original photo visible peeking under the gown ✓, identity ~95% match, full-body framing ✓. Minor residual drift: closed-mouth smile vs original wide smile; hands hidden by gown drape (reasonable physical adaptation since "hands in pockets" doesn't transfer to a pocketless gown). **Locked v3 as the v1 baseline prompt.**

**Lessons for future prompt iteration:**
- Nano Banana 2 interprets multi-image prompts compositionally. Listing what to take *and what NOT to take* PER IMAGE, separately, is far more effective than a blanket "ignore that person."
- Pose preservation needs an explicit physical-adaptation escape hatch. Strict pose preservation across incompatible garment types (suit → gown) produces awkward results; the minimal-adaptation language was the right balance.
- The aspect-ratio mapper enum MUST match the API's supported set exactly.
- Latency for the preview model is highly variable across calls — 19s, 33s, 58s on consecutive identical-input calls. Don't conclude "the prompt is broken" from a single slow generation.

### 2026-05-13 — UI hang bug: `use_container_width` past removal date

User reported the Streamlit UI hanging on "Generating…" indefinitely. Terminal log proved the API call succeeded (`[llm] finish_reason=STOP` printed), but the result never reached the UI.

**Root cause:** `app.py` used `use_container_width=True` on every `st.image`, `st.button`, and `st.download_button`. Streamlit deprecated this parameter with a removal date of 2025-12-31; today (2026-05-13) is over four months past that. Streamlit 1.57 still warns rather than errors, but the resulting behavior on layout was inconsistent enough to leave the post-API rerun in a broken state.

**Fix in `app.py`:**
- Replaced every `use_container_width=True` with `width="stretch"` per the deprecation migration guide.
- Wrapped the post-generation save block in try/except so any save error surfaces a friendly error instead of crashing silently.
- Added diagnostic `print()` statements bracketing the post-API flow: `[app] generate_tryon returned: ...`, `[app] saved result to ...`, `[app] state updated; calling st.rerun()`. Future hangs are now traceable by inspecting the terminal.

**Lesson:** Streamlit parameter deprecations now have removal dates — `use_container_width` was just the first. Check the Streamlit changelog and update wherever a `will be removed after YYYY-MM-DD` warning appears in the terminal, even if the app appears to still work.

### 2026-05-13 — UI hang #2: nested `with result_col: with st.spinner` deadlock

After the `use_container_width` fix and a hard Streamlit restart, the UI still hung — but at a different point. Diagnostic prints traced the hang to *after* `generate_tryon` returned successfully but *before* exiting the `with st.spinner(...)` and `with result_col:` blocks.

Sequence observed in terminal (all prints fired):
```
[app] Generate button clicked, entering generation flow
[app] about to call generate_tryon
[llm] finish_reason=STOP content=True parts_raw_is_none=False parts=1 inline_data_parts=1 text_parts=0
[llm] decoding image: mime=image/jpeg bytes=476932
[llm] decoded: (848, 1264) RGB
[app] generate_tryon call completed (returned without raising)
```

Then silence. The next print (`[app] exited spinner block`) never fired — meaning the script was hanging at the `with` block exit.

**Root cause:** the spinner was nested inside a *re-entered* column context. `result_col` was already opened earlier in the script (to render the existing result or the placeholder caption), and we were re-entering it later to wrap the spinner. After a 20–60s blocking API call, the combination of (re-entered column) × (spinner cleanup) × (Streamlit's WebSocket state) deadlocks the layout.

**Fix in `app.py`:** removed the `with result_col:` wrap around the spinner. The spinner now appears in the main page flow (just above the columns) during generation. The result still lands in `result_col` correctly on the next rerun — that happens via session state, not via re-entering the column context here.

**Diagnostic infrastructure added during this debug session (kept in place for future debugging):**
- `llm.py`: a `log = functools.partial(print, flush=True)` helper, used for all diagnostic prints. Critical because Streamlit's stdout under a pipe is block-buffered — without `flush=True`, prints can sit invisibly in a buffer for many seconds.
- `llm.py`: rich anatomy print after every API response: `finish_reason`, `content` present, `parts_raw_is_none`, total parts, inline-data parts, text parts. Plus per-decode prints showing MIME type and byte count.
- `app.py`: prints at every decision point in the click handler — entry, before/after API call, after each save step, before rerun.

**Lessons:**
- Don't re-enter the same Streamlit column context across long async/blocking operations. Prefer flat layout calls inside `if clicked:` handlers.
- Block-buffered stdout under Streamlit means `print()` without `flush=True` is unreliable for tracing live execution. Use a flushing helper for any diagnostic logging.

### 2026-05-13 — Prompt v4: subject's body is the canvas

User flagged a quality issue after the first end-to-end successful generation: the subject's BODY was being reshaped to match the outfit reference (mannequin's slim, elongated proportions), rather than the outfit being adapted to fit the subject's actual body. Exact inversion of the desired behavior.

**Root causes in v3 prompt:**
1. Body shape / proportions / height / build were NOT in the "take from FIRST IMAGE" list. The model was free to source body shape from anywhere.
2. "Silhouette" and "drape" were listed under "take from SECOND IMAGE." But these are exactly the things that depend on the wearer's body — a kurta drapes differently on different builds. Telling the model to take the drape from the outfit ref implicitly says "use the mannequin's body shape."
3. No explicit "garment adapts to subject, not vice versa" anchor.

**Decisions made (via grill questions):**
- Surgical refactor (keep v3 structure, add body constraints) over full restructure.
- "Body preservation always wins" when in tension with fashion-photography polish.

**v4 changes vs v3:**
- Top of prompt: explicit framing — *"THE SUBJECT'S BODY IS THE CANVAS — every other element adapts to it."*
- Added **`body shape, body proportions, height, build, weight, silhouette, body type`** to the FIRST IMAGE "take ONLY" list with `Do NOT slim, elongate, lengthen, idealize, or reshape`.
- Removed `silhouette` and `drape` from the SECOND IMAGE "take" list. Replaced with `construction style (A-line, fitted, oversized, flared, straight-cut)` and `length category` — properties of the garment itself, independent of who wears it.
- Added **`the reference body's shape, proportions, height, build, or silhouette`** to the "do NOT take from SECOND IMAGE" list, with CRITICAL marker.
- Added a **CRITICAL — body-fit adaptation principle** section: garment fits subject as-is, doesn't reshape; if garment was tailored to a slim mannequin but subject is fuller, the garment drapes differently on the subject — that's correct and expected.
- Added explicit *"Do NOT idealize, flatter, slim, elongate, or otherwise 'fashion-model' the SUBJECT'S figure"* to the identity section.

**v4 test result (23.3s, 848×1264, same red-kurta + beige-suit inputs):**
- Body proportions now look like the subject's actual build, not the mannequin's elongated figure. ✓
- Original sneakers visible peeking out under the kurta hem (confirming full-body framing). ✓
- Identity, hair, skin, background, outfit fidelity all preserved. ✓
- Locked v4 as the new baseline prompt.

**Lesson for prompt iteration:** when a Gemini multi-image prompt lists `silhouette` or `drape` under the outfit-reference image, the model can interpret that as license to import the body shape too. Be careful to list only *intrinsic garment properties* (cut, construction, length category, color, pattern) under the outfit-reference, never properties that are inherently a function of the wearer's body.

### 2026-05-13 — Tier B implemented: outfit preprocessing pipeline

After v4 testing still showed visible body-bleed (subject slimmed/elongated to match the mannequin's proportions in the red-kurta test), realized prompt-only iteration had hit a structural ceiling. Held a grilling session and committed to **Tier B: outfit-image preprocessing** — a pre-stage that converts any messy outfit photo (mannequin / model / cluttered background) into a clean garment-only flat-lay before the main try-on call.

**Why this works:** the root cause of body-bleed is visual weight in the outfit input. Gemini multimodal weights visual signals heavily; text instructions like *"don't slim the subject"* cannot fully override a high-contrast image of a slim mannequin wearing the garment. Removing the mannequin from the input removes the visual anchor entirely.

**Architectural decisions (locked via grilling, all "Recommended" options taken):**

| # | Decision | Locked value |
|---|---|---|
| B.1 | Intervention tier | Tier B — outfit-image preprocessing |
| B.2 | Preprocessing method | Gemini-based extraction (no new dependencies) |
| B.3 | Cleaned-outfit style | Clean e-commerce flat-lay on pure white (zero body anchor) |
| B.4 | Pipeline UX | Two-phase spinner; intermediate hidden from UI but saved to disk |
| B.5 | Failure handling | Soft fallback to raw outfit + v4 prompt; quiet disclosure caption on result |
| B.6 | Main (Stage 2) prompt | Keep v4 unchanged for both happy path and fallback |
| B.7 | Caching | SHA-256 hash of preprocessed outfit bytes → `images/cache/{hash}.png`; no TTL |

**Pipeline (per Generate click):**

```
1. Preprocess uploads (RGB / EXIF / resize <=1536px)
2. Stage 1 — extract_garment(outfit):
     cache hit  → return cached cleaned outfit (~0.05s)
     cache miss → Gemini call with EXTRACT_GARMENT_INSTRUCTION (~15-30s)
     failure    → fall through with raw preprocessed outfit + status='fallback'
3. Stage 2 — generate_tryon(person, cleaned_outfit) with v4 prompt (~15-30s)
4. Save: images/{ts}_person.png, _outfit.png, _outfit_cleaned.png (if not fallback);
         generated/{ts}_tryon.png
5. Display result + (if fallback) caption: "Outfit preprocessing was unavailable;
   body-shape fidelity may be reduced."
```

**File changes:**
- `prompt.py` — added `EXTRACT_GARMENT_INSTRUCTION` constant (1594 chars). Defines the Stage 1 prompt: render the input as a clean product flat-lay on pure white, remove all person/mannequin/background/accessories, preserve garment colors/patterns/embroidery/cut.
- `llm.py` — refactored. Added `import hashlib`, `CACHE_DIR = Path("images/cache")`. Factored the Gemini-call-and-parse logic into a private `_generate_image(prompt_text, images, aspect_ratio, label)` helper used by both functions. New `extract_garment(outfit_img) -> (Image, status)` with content-hash disk caching and soft fallback. `generate_tryon(person, outfit)` unchanged in signature but now uses the shared `_generate_image` helper.
- `app.py` — split the single spinner into two named phases (*"Cleaning up the outfit image…"* then *"Composing your try-on…"*). Added `preprocess_status` to session state. Saves cleaned outfit to `images/{ts}_outfit_cleaned.png` only when extraction succeeded. Disclosure caption rendered under the result image when `preprocess_status == "fallback"`. Stripped the verbose `[app]` diagnostic prints that were added during the hang-debug cycle; kept the `[app]` error-context prints and all `[llm]` prints.

### 2026-05-13/14 — v6 attempt (3-image color reference) + rembg pivot

User flagged color/design drift on a dusty-mauve kaftan: the result came back as taupe/beige. The garment had a distinctive yellow inner panel and gold embroidery; those survived, but the body color was clearly shifted toward "tasteful neutral."

Test results: drift was *still present*. Ran a diagnostic with `[neutralized person, raw outfit only]` and got nearly identical drift. **Conclusion: drift is happening in Stage 3's generative rendering itself, not just Stage 1's flat-lay extraction.** Prompts asking Gemini to "use these exact colors" have a structural ceiling — the preview Flash model's training bias toward muted-neutral product photography overrides explicit instructions for nuanced colors.

**Pivot: non-generative Stage 1.** Replaced the generative `extract_garment` (Gemini call with prompt) with `rembg` using the `u2net_cloth_seg` model. This is a small (~170 MB) ONNX cloth-segmentation model that runs locally — it doesn't re-render the garment, it just cuts out the actual garment pixels with alpha-masked background. Composited onto white. Result: pixel-accurate color preservation from the input.

**`u2net_cloth_seg` output quirk:** the model returns a 3×-height stacked output corresponding to three garment classes (upper-body, lower-body, full-body). For multi-piece outfits like kurta + dupatta + salwar, the upper and lower segments contain different pieces. We composite all three onto a single white canvas via `Image.alpha_composite`. Single-class garments (a saree, a dress) produce only one populated segment; the empty segments composite as no-ops.

**Implementation changes:**
- `prompt.py`: removed `EXTRACT_GARMENT_INSTRUCTION` (no longer used — Stage 1 is non-generative now). Removed the v6 3-image `TRY_ON_INSTRUCTION` and renamed `TRY_ON_INSTRUCTION_FALLBACK` back to `TRY_ON_INSTRUCTION` (single 2-image v5 prompt).
- `llm.py`: `extract_garment` now uses `rembg.remove()` + `Image.alpha_composite` over three segments. `_get_rembg_session()` lazy-loads the ONNX model once per process. - `app.py`: dropped the `original_outfit_ref` wiring. Still three sequential spinners, still saves cleaned outfit + neutralized person to disk, still merges fallback disclosures.

**Dependency change:** added `rembg[cpu]` via `uv add` (pulled in `onnxruntime`, `numba`, `scipy`, `scikit-image`, etc.). Model file `u2net_cloth_seg.onnx` lives at `~/.u2net/u2net_cloth_seg.onnx` (~169 MB) — downloaded once, reused forever. **Lessons:**
- **Generative models cannot be reliably forced to preserve specific colors via prompts and visual references when their training bias points elsewhere.** Confirmed by v6's failure: even with the original photo passed as an explicit third image and the prompt saying "the THIRD IMAGE wins on colors," Gemini still drifted toward its training-distribution neutrals.

- **Multi-class segmentation models have non-obvious output shapes.** `u2net_cloth_seg` returns 3× height stacked segments; assuming a single-class output would lose pieces of a multi-garment outfit. Always inspect a tool's output structure before integrating.

- The 170 MB rembg model needs to be present on every machine that runs the app. Setup-script the download. Consider switching to a lighter segmentation model (`silueta` is ~43 MB) if startup time on fresh installs matters.
- The "always run rembg" policy may be wasteful for outfit photos that are already clean flat-lays. A heuristic skip (e.g., detect uniform white background) could save 3.5s per generation — but adds complexity. Defer until measurable.

New order: (1) KIND OF OUTFIT / STYLE — dominant signal, with explicit "garment-type match outweighs every other factor" and "never let a perfect size or color override a clear style mismatch"; (2) Size match — secondary, used to rank among style-matching candidates; (3) Color match — tertiary, final tie-breaker. Added a CRITICAL block enumerating the priority-violation prohibitions. Updated the per-pick reason examples to LEAD WITH the garment-type match.
- `catalog.py` — rewrote `rule_fallback_top3` to honor the same priority. Old logic was tiered (exact size+color → exact size → exact color → alphabetical) with no style awareness. New logic is score-based: style match = +1000, size match = +100, color match = +10. Style match always outweighs size+color combined. Style is detected via simple substring match of any token in the user's `name` query against the product name (lowercased). Reasons now lead with the style-match status and explain mismatches honestly.

**Test results (smoke test against current 10-product catalog):**
- `{name: "kurta", size: "M", color: "Blue"}` → P07 (kurta XL Yellow), P06 (kurta XXL Off-White), then P04 (Floral Dress M Blue) as third. Kurta products correctly beat the perfect-size-perfect-color dress.
- `{name: "dress", size: "XL", color: "Black"}` → P08, P10, P04 — all 3 dresses in the catalog. Size-XL dress ranks first via the secondary signal.
- `{name: "jumpsuit"...}` → P05 (the only jumpsuit) first regardless of size/color mismatch.
- `{name: "saree"...}` → no saree exists in catalog, falls through to size-XL off-style fallbacks with honest "this isn't a 'saree' style" reasons.

**Known rule-fallback edge case (not LLM-path):** the substring matcher doesn't connect related synonyms — typing "kurta" won't match "Kurti" or "Kurtha" products. The LLM ranker understands these synonyms; the rule fallback doesn't. Acceptable trade-off since the fallback is the rare path. If the demo needs this, options are: stem matching (first-N-chars), explicit synonym map, or letting the rule fallback go through the LLM with a tiny "just rank, no images" prompt (loses determinism).

### 2026-05-14 — Browse catalog tab (third tab)

Added a third Streamlit tab — **Browse catalog** — that renders all products from `products/catalog.json` as a read-only grid. Pure display surface; no try-on, no LLM, no per-card actions. Useful for verifying catalog setup and as a "what's in the store" intro for users.

**Layout:** 3-column grid, rows of 3 with the last row holding the remainder. Each card has the raw product image (or a `(image missing — add a file at products/raw/{id}.jpg)` caption if the file isn't on disk), bold product name, `Size: X` / `Color: Y` line, and an `ID: P0X` caption.

**Display tab order:** `Manual try-on` | `Catalog recommendations` | `Browse catalog`. Added at the end to preserve existing user habit (recommendations stays at position 2).

**Code-order detail (important if you ever refactor):** `with tab_browse:` is positioned BEFORE `with tab_catalog:` in `app.py` script order, even though it's the third tab visually. This is because `tab_catalog` uses `st.stop()` on the catalog-missing path, which halts the entire script. If `tab_browse` came after `tab_catalog` in code, a missing/malformed `products/catalog.json` would silently leave the browse tab empty instead of showing its own error. By rendering `tab_browse` first in code, it gets to display its own `st.error()` before `tab_catalog` can halt anything.

**Other refactors to `app.py`:**
- **Catalog load lifted to module top.** Previously `load_catalog()` was called inside `with tab_catalog:`. Moved to a top-level try/except that sets `_catalog` and `_catalog_error` once per Streamlit run. Both `tab_browse` and `tab_catalog` consume these. Saves a duplicate JSON parse on every rerun and centralizes the "catalog missing" error path.
- **`st.tabs` extended** from 2 entries to 3: `st.tabs(["Manual try-on", "Catalog recommendations", "Browse catalog"])`.

**No new types, no new prompt, no new dependencies.** Uses the existing `Product` dataclass from `catalog.py` and its `raw_path` property to locate images.
